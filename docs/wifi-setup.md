# Changing a printer's Wi-Fi network from the demo page

An investigation into configuring the wireless settings of a USB-connected
Brother QL from the static demo site, with a plan for building it. Nothing in
this note is implemented yet.

## Summary

It is feasible, and it fits the library as it stands. Brother's own
iPrint&Label app sets Wi-Fi credentials by writing a short **PJL text command**
down the ordinary printer data channel — the same bulk OUT endpoint every print
job uses — and reading a text reply back on the bulk IN endpoint. That is
exactly what `UsbTransport` already drives over WebUSB. The format was
reverse-engineered from the app's native library and published in August 2026
by the `mb-cli-printer` project; see [Sources](#sources).

Two things are missing today:

1. **The transport cannot return a text reply.** The USB read loop hands every
   incoming byte to `StatusFramer`, which keeps only 32 byte `80 20 42` status
   packets and discards the rest as "resync" noise. The Wi-Fi replies are
   plain ASCII, so they need a raw-capture path that bypasses the framer.
2. **Nobody has hardware-tested the credential-bearing write.** The read-only
   half (query current network state, scan for access points, system report)
   was validated on a QL-1110NWB by the `mb-cli-printer` author. The settings
   write was generated byte for byte from the disassembled app but never sent
   to a printer. The first run from this page will be that test, so the plan
   below front-loads the harmless read-only steps and makes the bytes
   inspectable before anything is applied.

Brother's official route (the Windows/macOS Printer Setting Tool, or its
`.bin` "command file" applied in mass-storage mode) is undocumented at the byte
level and needs a Brother driver or a mass-storage interface, neither of which
a browser can use. The WPS button and Wireless Direct's web page remain the
no-code fallbacks and the way back if a bad credential is applied.

## What was ruled out

| Route | Why not |
| --- | --- |
| Brother's raster / ESC/P / P-touch Template command references | Fetched and searched the QL-800/810W/820NWB raster, ESC/P and P-touch Template PDFs. They document `ESC i S`, `ESC i a`, `ESC i z`, `ESC i M`, `ESC i K` and the `ESC iX..` template settings. No wireless command of any kind. |
| Printer Setting Tool "Save in Command File" (`.bin`) | Brother's developer pages describe the workflow only ("The file extension is .bin", "use the mass storage mode"). No format. Producing one needs Windows or macOS and Brother's driver; applying it via mass storage needs a USB class browsers refuse to open. It is still useful as a *validation* artefact: if someone exports one for a known SSID, its bytes can be diffed against ours. |
| `ESC i U` / `ESC i X` device-settings protocol (`brother-label-settings`) | Covers auto power off, density, command mode and so on. Its author states Wi-Fi and Bluetooth settings are not covered. It confirms the `ESC @`, `ESC i a 01` preamble convention that the reboot command below also follows. |
| Brother's mobile Print SDK | Closed source; no documented wireless-setup API. |
| SNMP / embedded web server | Only reachable once the printer is already on a network. Chicken and egg for this use case. |

## The protocol

Everything below comes from `docs/brother-wireless-config.md` in
`MakersBrain/mb-cli-printer` (AGPL-3.0), which disassembled
`libnative-lib.so` from iPrint&Label. The protocol facts are reproduced here;
code must be written fresh for this repository (see [Licensing](#licensing)).

### Envelope

Every request is a PJL job, bracketed by the universal exit language sequence:

```text
ESC %-12345X @PJL \r\n          1b 25 2d 31 32 33 34 35 58 40 50 4a 4c 0d 0a
@PJL <one line per parameter> \r\n
ESC %-12345X                    1b 25 2d 31 32 33 34 35 58
```

Parameters are Brother's `OBJBRNET` object with a *numeric* id (not a dotted
SNMP OID):

```text
@PJL DEFAULT OBJBRNET="<id>:<value>"\r\n
```

### Reading a value

A getter is two lines in one job. Either line on its own gets `Invalid object
ID` or silence:

```text
@PJL DEFAULT OBJBRNET="458867"\r\n
@PJL INQUIRE OBJBRNET\r\n
```

The reply is text containing `458867:1`-style pairs. Ids seen on a
QL-1110NWB:

| Id | Meaning | Value format |
| --- | --- | --- |
| `458867` | Wi-Fi connected | `0` / `1` |
| `458967.2` | IPv4 address | hex octets, `-c0-a8-01-2a` |
| `458877` | Current SSID | UTF-8 bytes as `-xx` hex pairs |
| `458880` | Encryption | enum below |
| `458881` | Authentication | enum below |
| `459138.2` | Infrastructure mode on | `0` / `1` |
| `459138.3` | Wireless Direct on | `0` / `1` |

### Scanning for networks

Two jobs: start the search, wait a few seconds, then ask for results.

```text
@PJL DEFAULT OBJBRNET="458845:31-3a"\r\n      (start scan)
@PJL INFO AVAILABLEWLAN\r\n                    (fetch results)
```

The result is CSV-like rows beginning `VAP`: column 1 SSID (hex-encoded),
column 4 channel, column 5 signal, column 6 `3` for enterprise, column 7 `2`
for encrypted. A QL-1110NWB returned two rows in a 285 byte reply spread over
five bulk IN transfers of at most 64 bytes.

### Writing the settings

One job with the parameters in this exact order, followed by a 14 byte
binary reboot command outside the PJL envelope:

| Id | Value |
| --- | --- |
| `458867` | `0` |
| `458878` | `1` |
| `458877` | SSID: UTF-8 bytes as lowercase `-xx` hex pairs (`-4d-61-6b-65-72` for `Maker`) |
| `99458890` | obfuscated passphrase, when authentication is WPA-PSK, WPA-only or WPA2-only |
| `99458889.1` | obfuscated key, when encryption is WEP |
| `458880` | encryption enum |
| `458881` | authentication enum |
| `459138.2` | `1` for infrastructure |
| `459138.3` | `1` for Wireless Direct (the app sends `0`) |
| `458865` | `1` |

```text
reboot: 1b 69 58 2a 31 03 00 01 2e 00 00 00 2c 00     (ESC i X * 1 ...)
```

The passphrase is XOR-obfuscated with a fixed repeating 16 byte key
`0d ae e4 a1 8b 7f 26 5e 72 5b 17 7a 71 cd ec 4d`. This is not encryption:
anyone holding the bytes holds the password.

Enums (decimal in the command):

| Encryption | | Authentication | |
| --- | --- | --- | --- |
| none | 1 | open | 1 |
| wep | 2 | shared-key | 2 |
| tkip | 3 | wpa-psk | 3 |
| aes | 4 | leap | 7 |
| ckip | 5 | eap-fast | 13 |
| cmic | 6 | peap | 15 |
| ckip-cmic | 7 | eap-ttls | 16 |
| tkip-aes | 8 | eap-tls | 17 |
| | | wpa-only | 18 |
| | | wpa2-only | 19 |

A home WPA2 network is `wpa-psk` + `tkip-aes`, which is what the app sends
by default. The QL-820NWB manual says enterprise (EAP) networks are not
supported, so the page should offer only open, WEP and the three WPA-PSK
variants.

After the reboot command the printer restarts. Over USB that is a device
disconnect: the transport's read loop rejects, `disconnect` fires, and the
page has to reconnect once the printer is back (typically 20 to 40 seconds).

### Verifying afterwards

Either repeat the getters (`458867` connected, `458967.2` IPv4, `458877`
SSID), or request the read-only **system report** with `1b 69 58 47`
(`ESC i X G`). The report is about 4.6 KB of INI-style text behind a two byte
binary prefix, with `[WLAN]`-style sections carrying SSID, IP and MAC. The
report is the better diagnostic; the getters are the better UI.

## Which printers

Models in this library that have Wi-Fi: QL-710W, QL-720NW, QL-810W,
QL-820NWB, QL-1110NWB, QL-1115NWB, PT-P750W, PT-P900W. iPrint&Label targets
the same set, so the command is expected to work across them, but the only
hardware evidence is read-only traffic on a QL-1110NWB. The QL-810W this
repository has printed on is a natural first target.

## Plan

### 1. Library: a raw exchange on the transport

`src/usb/transport.ts` gains a raw-capture mode. Sketch:

```ts
// Transport (optional member, so the bridge can add it later)
exchange?(request: Uint8Array, options: ExchangeOptions): Promise<Uint8Array>;

interface ExchangeOptions {
  /** Give up if nothing at all arrives within this long. */
  firstReplyMs: number;
  /** Once something has arrived, resolve after this much silence. */
  idleMs: number;
}
```

Inside `UsbTransport`, a `#rawSink` field. While it is set the read loop
appends incoming bytes to the sink and resets its idle timer instead of
feeding the framer. `exchange()` installs the sink, writes the request
through the existing chunked `write()`, and returns the concatenated bytes.
Rules:

- Mutually exclusive with status traffic: callers go through the core's
  `acquire()` lock so a print and an exchange cannot interleave, and the
  status queue is cleared before and after. A stray 32 byte status packet
  that arrives mid-exchange is simply part of the raw bytes; the parser
  ignores it.
- The reply is text with no length prefix and no terminator, so the end is
  detected by silence. 250 ms idle after a 3 s first-reply budget is what
  `mb-cli-printer` uses and what the QL-1110NWB tolerated.
- A disconnect during an exchange rejects with `DeviceDisconnectedError`, as
  elsewhere. For the settings write, that rejection is the expected outcome
  and the caller treats it as "the printer is rebooting".

Tests, with `test/util/mock-usb.ts`: reply split across several reads;
nothing arrives (first-reply timeout); reply interleaved with a status
packet; unplug mid-reply; a second exchange while one is pending is refused.

### 2. Library: a DOM-free `src/wifi.ts`

Pure builders and parsers, exported from the package root and as a `./wifi`
subpath so a consumer can take it without the imaging pipeline:

- `encodeSsid`, `obfuscatePassphrase` (an involution; test both directions)
- `buildInquiry(id)`, `buildScanStart()`, `buildScanResults()`,
  `buildWifiSettings(settings, { reboot })`, `SYSTEM_REPORT_COMMAND`
- `parseObjbrnetValue(reply, id)`, `parseAccessPoints(reply)`,
  `parseIpv4(reply)`, `parseSystemReport(reply)`
- `WifiSettings` type with validation: non-empty SSID, a passphrase whenever
  authentication is not open, open implies encryption none, and the
  WEP-versus-WPA parameter selection.

A byte-exact golden test pins the command for a fixed SSID and passphrase so
a later refactor cannot silently reorder parameters. Parsers get fixtures
synthesised from the documented row and pair formats, replaced by real
captures as soon as a hardware run saves some.

A thin `WifiClient` (or methods on `BrotherQLPrinterCore`) ties the two
together under the busy lock: `readNetworkState()`, `scanNetworks()`,
`applySettings()`, `systemReport()`.

### 3. The page

A third entry in `demo/vite.config.ts` next to `main` and `diagnostics`,
served at `/brother_ql/wifi/`, linked from the demo header. A separate page
keeps the credential form off the printing demo and mirrors the diagnostics
wizard's structure. Steps, top to bottom:

1. **Connect** (reuses the demo's pairing code and troubleshooting panel).
2. **Current network**: SSID, connected, IPv4, mode. This is the harmless
   first exercise of the raw-reply path on the user's own printer.
3. **Scan**: populates an SSID picker with channel, signal and security;
   a free-text field remains for hidden networks.
4. **Credentials**: SSID, passphrase (masked, with a reveal toggle),
   security preset (WPA/WPA2 personal by default; open; WEP). Never written
   to `localStorage`.
5. **Review**: the exact bytes as a hex and text dump with the passphrase
   masked, plus a *Download .bin* button for anyone who wants to send it by
   another tool or compare it with a Printer Setting Tool export.
6. **Apply**: an explicit confirmation naming the SSID. Sends the command,
   expects the disconnect, and shows "the printer is restarting".
7. **Reconnect and verify**: `watchConnectionEvents` re-pairs when the
   device reappears; the page polls the connected flag and IPv4 for up to a
   minute and then shows the address, with a pointer to the bridge README for
   printing to it over the network.

Each step records its raw reply so a failed run can be turned into a bug
report, but these recordings must exclude the settings command: the
diagnostics recording proxy logs the first bytes of every `transferOut` as
hex, and a PJL command's first bytes include the SSID.

### 4. Documentation

A README section under the demo, a line in the hardware verification table
per model, and a CHANGELOG entry.

## Risks

- **Unvalidated write.** The command is assembled from the app's disassembly,
  not from a capture. If the printer rejects it, nothing happens and the
  current network stays. If it accepts a wrong value, the fix is the WPS
  button, Wireless Direct plus the embedded web server, or Brother's tool.
  The parameter order, the trailing `458865`, and `458878` are the least
  understood parts.
- **Reboot cost.** The write always restarts the printer; a cancelled job or
  an unrelated open tab holding the device will see a disconnect.
- **Credential handling.** The obfuscation is reversible. The page is static
  and talks only to the printer, so nothing leaves the machine, but the bytes
  must stay out of logs, bundles and storage.
- **Model spread.** Older Wi-Fi models (QL-710W, QL-720NW, PT-P750W) may
  predate the OBJBRNET firmware path. The read-only steps will show quickly
  whether a given printer speaks it at all.
